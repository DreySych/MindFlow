1. В приложении ИИ‑поиска используется паттерн проектирования «Стратегия».

    Где реализован паттерн:
        Файл ai/strategies.py:
            SearchStrategy — абстрактный интерфейс стратегии.
            AllQuestionsStrategy — стратегия «взять все вопросы».
            LastNQuestionsStrategy — стратегия «взять только последние N вопросов».

        Файл ai/services.py:
            AiSearchService — Context для паттерна «Стратегия».
            В конструкторе AiSearchService принимает объект SearchStrategy и хранит его в self.strategy.
            Метод set_strategy(self, strategy) позволяет менять стратегию.
            Внутри search() сервис не знает деталей выборки постов, а просто вызывает self.strategy.get_questions(user_query).

        Файл ai/views.py:
            В ai_search_api перед вызовом service.search(query) выбирается нужная стратегия.

    Зачем:
        Разделение ответственностей:
            AiSearchService отвечает только за общую операцию ИИ‑поиска (сбор контекста, формирование промпта, запрос к Ollama),
            а выбор конкретного набора вопросов вынесен в отдельные стратегии (AllQuestionsStrategy, LastNQuestionsStrategy). Это
            уменьшает связность и упрощает чтение и поддержку кода.

        Взаимозаменяемые алгоритмы поиска:
            Разные способы отбора постов (все вопросы, только последние N, в будущем — по рейтингу, только с ответами и т.п.)
            реализуются как отдельные классы, но имеют общий интерфейс SearchStrategy. Это позволяет добавлять новые варианты
            поиска без переписывания сервиса и views.py.

    В итоге паттерн «Стратегия» здесь применяется для изоляции алгоритмов выбора контента для LLM от общей логики ИИ‑поиска
    и для обеспечения лёгкого расширения и переключения режимов поиска в системе.

2. В проекте используется паттерн проектирования «Фабричный метод» (Factory Method).

    Где реализован паттерн:
        Файл main/model_loader.py:
            get_model() — функция, которая отвечает за создание и получение модели эмбеддингов.

        Файлы main/views.py и questions/views.py:
            Код не создаёт модель напрямую, а получает её через get_model().

    Зачем:
        Сокрытие создания объекта:
            View-функции не знают, какая конкретно модель используется и как она загружается.
            Они просто вызывают get_model() и получают готовый объект.

        Упрощение замены модели:
            Если нужно заменить модель эмбеддингов или способ её загрузки, изменения нужно внести только в main/model_loader.py,
            а не во все места проекта, где используется поиск или создание эмбеддингов.

    В итоге паттерн «Фабричный метод» используется для централизованного создания модели машинного обучения
    и уменьшения зависимости основного кода от конкретного способа инициализации модели.

3. В проекте используется паттерн проектирования «Адаптер» (Adapter).

    Где реализован паттерн:
        Файл ai/clients.py:
            OpenRouterClient — адаптер для работы с внешним API OpenRouter.

        Файл ai/services.py:
            AiSearchService обращается не к сырому API напрямую, а к OpenRouterClient.

    Зачем:
        Изоляция внешнего API:
            OpenRouter возвращает ответ в своём JSON-формате, который неудобно использовать напрямую во всём проекте.
            Адаптер преобразует внешний ответ в простой формат, понятный проекту: текст ответа или сообщение об ошибке.

        Упрощение замены провайдера:
            Если в будущем нужно заменить OpenRouter на другой AI-сервис, основную логику проекта менять не придётся.
            Достаточно будет изменить адаптер.

    В итоге паттерн «Адаптер» используется для отделения внешнего AI API от внутренней логики проекта
    и приведения ответа нейросети к единому формату, удобному для приложения.
