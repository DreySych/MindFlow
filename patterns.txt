1. В приложении ИИ‑поиска используется паттерн проектирования «Стратегия».

    Где реализован паттерн:
        Файл ai/strategies.py:
            SearchStrategy — абстрактный интерфейс стратегии.
            AllQuestionsStrategy — стратегия «взять все вопросы».
            LastNQuestionsStrategy — стратегия «взять только последние N вопросов».

        Файл ai/services.py:
            AiSearchService — Context для паттерна «Стратегия».
            В конструкторе AiSearchService принимает объект SearchStrategy и хранит его в self.strategy.
            Метод set_strategy(self, strategy) позволяет менять стратегию.
            Внутри search() сервис не знает деталей выборки постов, а просто вызывает self.strategy.get_questions(user_query).

        Файл ai/views.py:
            В ai_search_api перед вызовом service.search(query) выбирается нужная стратегия.

    Зачем:
        Разделение ответственностей:
            AiSearchService отвечает только за общую операцию ИИ‑поиска (сбор контекста, формирование промпта, запрос к Ollama),
            а выбор конкретного набора вопросов вынесен в отдельные стратегии (AllQuestionsStrategy, LastNQuestionsStrategy). Это
            уменьшает связность и упрощает чтение и поддержку кода.

        Взаимозаменяемые алгоритмы поиска:
            Разные способы отбора постов (все вопросы, только последние N, в будущем — по рейтингу, только с ответами и т.п.)
            реализуются как отдельные классы, но имеют общий интерфейс SearchStrategy. Это позволяет добавлять новые варианты
            поиска без переписывания сервиса и views.py.

    В итоге паттерн «Стратегия» здесь применяется для изоляции алгоритмов выбора контента для LLM от общей логики ИИ‑поиска
    и для обеспечения лёгкого расширения и переключения режимов поиска в системе.

2. В проекте используется паттерн проектирования «Сервисный слой» (Service Layer).

    Где реализован паттерн:
        Файл ai/services.py:
            AiSearchService — отдельный сервис, который содержит основную бизнес-логику ИИ-поиска.
            Он отвечает за сбор данных, формирование промпта, обращение к Ollama и возврат результата.
    
        Файл ai/views.py:
            View не выполняет всю логику ИИ-поиска самостоятельно.
            Она только получает запрос пользователя, выбирает стратегию и вызывает service.search(query).

    Зачем:
        Разделение ответственностей:
            Логика ИИ-поиска не смешивается с обработкой HTTP-запросов.
            Views отвечают за получение данных от пользователя и возврат ответа,
            а AiSearchService отвечает за саму работу ИИ-поиска.

        Упрощение поддержки:
            Если нужно изменить промпт, способ обращения к Ollama или обработку результата,
            это можно сделать в ai/services.py, не переписывая views.py.

    В итоге паттерн «Сервисный слой» используется для вынесения бизнес-логики ИИ-поиска в отдельный класс,
    чтобы код был более понятным, разделённым и удобным для дальнейшего расширения.


3. В проекте используется паттерн проектирования «Наблюдатель» (Observer).

    Где реализован паттерн:
        Файл questions/models.py:
            Используются Django Signals:
                post_save — сигнал, который срабатывает после сохранения объекта.
                @receiver — обработчик, который автоматически реагирует на событие.

            Обработчики подписаны на события создания объектов:
                Question
                Answer
                Comment

    Зачем:
        Автоматическая реакция на события:
            Когда пользователь создаёт вопрос, ответ или комментарий,
            Django автоматически отправляет сигнал post_save.
            После этого обработчик создаёт нужные уведомления.

        Разделение логики:
            Логика создания уведомлений не находится напрямую во views.
            Она вынесена в отдельные обработчики сигналов.
            Благодаря этому код становится менее связанным и более удобным для поддержки.

    В итоге паттерн «Наблюдатель» используется для автоматического создания уведомлений после действий пользователей.
    Объект сохраняется, Django отправляет сигнал, а подписанный обработчик реагирует на это событие.
